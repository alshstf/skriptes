# Грабли и устройство подсистем — подробно

Полные версии разделов «Грабли» из CLAUDE.md. CLAUDE.md держит по каждой короткую выжимку и ссылку сюда; читать нужный раздел перед правкой соответствующей подсистемы.

### 1. Frontend bundle не обновляется после `docker compose build`

Vite хэширует имя бандла по контенту. Build context `../frontend` (в
`infra/docker-compose.yml`) — это чекаут, ИЗ КОТОРОГО запущен compose. Правки в
одном worktree, а `docker compose build` из другого (или из основного чекаута) →
build возьмёт старое содержимое и выдаст тот же хэш. Собирай из того worktree, где
правки (compose-проект у всех чекаутов один — `skriptes`, так что пересоберётся
тот же стек).

Если что-то не сходится — `docker compose build --no-cache frontend` снимает
кэш слоя COPY.

### 2. Жанры на фронте — display-имена и стиль чипов в нескольких местах

`book.genres` от Meili приходит как массив `fb2_code`'ов (строк). Display-имена
живут в Postgres + ежесборочный seed (см. `backend/internal/genres/`),
exposed через `GET /api/genres`. На фронте — `useGenreMap()` в
`frontend/src/lib/genres.ts`.

**Места рендера chips с жанрами:**
- `frontend/src/components/GenreChips.tsx` — одна строка + кликабельный «+N» поповер; список `/books` (BooksPage::BookCard)
- `frontend/src/components/BookListItem.tsx` — AuthorPage / SeriesPage (свои inline-`Badge`)
- `frontend/src/pages/BookDetailPage.tsx` — карточка книги (backend hydrate'ит `g.display` сам, useGenreMap не нужен)

**Стиль** чипов (приглушённый/контрастный) — персональная настройка «Внешний
вид»: класс берётся из `genreChipClass(useGenreChipStyle())`
(`frontend/src/lib/appearance.ts`); его используют и `GenreChips`, и
`BookListItem`. Правишь имена/стиль жанров — пройди по всем местам. Языки в
фильтре резолвятся через `useLanguageMap()` (`lib/content.ts`).

**Алиасы жанров** (#286): `backend/internal/genres/aliases.json` — код (нижний регистр) → код
словаря: алиасы из `genres.json` клиента FLibrary (`adv_all`=`adventure`, `painting`=`visual_arts`),
«…: прочее», совпадающие с нашими общими кодами (`humor_all`→`humor`), коды-слова и дефисные коды
litnet (`urban-fantasy`→`sf_fantasy_city`); неочевидные (`wuxia`, `action`) не сводим. Импорт сводит
при записи (`genres.CanonicalCodes` в `processRecord`), существующее переносит
`genres.MergeAliases` (книги, избранное, скрытые жанры в `content`, ручные правки; строка алиаса
удаляется) — разовый гейт `genre_aliases_merged_vN`, бампать при пополнении таблицы. Новый код
в словаре не должен совпадать с алиасом (тест `TestAliases_PointIntoDictionary`).

**Обогащённая плашка книги** (плотная строка сигналов, как у авторов): общий
компонент `frontend/src/components/BookMeta.tsx` (приём — структурный `BookMetaFields`,
поэтому годится и `BookListItem`, и `CollectionBook`) — год · 🌐 внешний рейтинг (Tooltip:
источник) · 📖 оценка читателей · 🎬 экранизация · язык · ✓/N% чтение · ★ избранное.
Используется в `BookListItem` (автор/серия), `BooksPage::BookCard` (/books) и `ShelvesPage`
(полки). НЕ-user сигналы (рейтинги/источник/экранизация) гидрирует `books.WorkMeta(ctx,
pool, workIDs) → map[workID]ListMeta` по work_id — зовут `books.HydrateListMeta` (для
`[]books.ListItem`: ListWorks + `catalog.GetAuthor/GetSeries`) и `collections.ListCollectionBooks`
(полки, свой DTO). User-сигналы (★/чтение) — в api-слое: `hydrateUserListMeta`
(`[]books.ListItem`) и `hydrateUserCollectionMeta` (`[]CollectionBook`), оба через
`history.FavoriteWorkSet` + `WorkReadStatusSet`. Suggest/Cmd+K плашку НЕ обогащаем
(минимальная, latency-sensitive).

### 3. `date_added` ≠ год написания книги

INPX'овский `date_added` — когда книга добавилась в библиотеку librusec, а не
когда автор её написал. Не использовать как proxy для creation date.

Настоящий год берём из fb2 (миграция 0012, два РАЗНЫХ поля — не смешивать):
- `books.written_year` — год написания / первого издания произведения.
  Источники по приоритету: fb2 `<title-info><date>` (локально — джоба обработки
  коллекции `metadata.Prewarmer`/`EnsureYearLocal`, под-тумблер «Года») →
  OpenLibrary `first_publish_year` → Wikidata `P577` (внешний rate-limited
  backfill-воркер `metadata.YearBackfillController`; per-source учёт попыток в
  таблице `book_year_lookups`, чтобы не долбить источник). Обе джобы — opt-in из
  админки **«Фоновые операции»**. По нему строится гистограмма «Книги по годам
  написания» (`catalog/service.go`); сюда же ляжет будущая bio-корреляция.
  `written_year_source` хранит происхождение.
- **Правдоподобие и год работы (#288, `metadata/work_years.go`).** fb2-дата врёт в основном ПОЗЖЕ
  настоящей (переиздание/перевод: «Хаджи-Мурат» 2020); сверка выборки с Фантлабом — совпадение
  83–87 %, поэтому «у переводов fb2 не брать» отвергнуто. Правила: fb2-год вне [1000, текущий] — нет
  года; позже года издания — год издания (`plausibleFb2Year`, источник `edition_year`); год РАБОТЫ =
  самый ранний из правдоподобных годов изданий и внешнего года `works.external_year` (Фантлаб: год
  первой публикации, приходит в том же ответе поиска, что и оценки «Известности», — `writeRenown`),
  потолок — самый ранний год издания; ручная правка неприкосновенна (`recomputeWorkYears`, его же зовёт
  `recomputeWorkAggregates`). Накопленное — разовый `CleanImplausibleBookYears` (гейт
  `work_years_v1`, на проде ~13 тыс. работ) + сброс found-строк Фантлаба, чтобы годы пришли сразу.
- `books.edition_year` — год конкретного бумажного издания этого fb2
  (`<publish-info><year>`). Справочное поле на карточке книги, в статистику НЕ
  идёт.

Meili-поле `year` (фильтр/сортировка/фасет «Год» на `/books`) тоже = `written_year`:
импорт его НЕ берёт из `date_added`, а синкает `importer.ResyncYears` — АВТОМАТИЧЕСКИ
(в конце импорта и после прохода прогрева/внешнего воркера, если год реально менялся;
ручной кнопки нет). Год наполняется обогащением ПОСЛЕ импорта, поэтому в поиске он
разрежён, пока обработка коллекции / внешний воркер не наполнят и не синкнут.

- **Опечатки и заглушки в годе работы** (#465, прод 2026-10: 25 работ, «Сами боги» Азимова — 1073). Правила
  в `recomputeWorkYears`:
  - год раньше рождения основного автора + 10 не берётся — только для родившихся с 1500 года (у
    средневековых дата рождения в Wikidata бывает с точностью до века);
  - год Фантлаба (`external_year_source='fantlab'`) сильнее fb2-года, который раньше него больше чем на 100 лет;
  - год издания раньше 1450 — заглушка, и равный ему fb2-год тоже. Исключение — старинная литература и
    фольклор (`antique*`/`folk*`/`epic`: «Филострато» — 1335). Набор таких изданий — через `JOIN`, не
    коррелированный `EXISTS`: тот план на проде упирался в минуты.
  - Годы жизни — `authors.born_year`/`died_year` (миграция 0057) и `ext_ids.wd_qid`. Их пишет
    `RecordingCandidateCheck`, когда поиск био принимает статью: факты из Wikidata политика приёма уже
    запрашивает. Догон — для авторов работ с годом < 1500 (гейт `author_lifetimes_suspect_v1`).
  - Полный пересчёт по новым правилам — гейт `work_year_rules_v1`. Шаг после импорта —
    `RecomputeYearsBeforeBirth`.

### 4. jsdom не делает CSS layout

Vitest + RTL гоняют в jsdom — `getBoundingClientRect()` всегда возвращает
нули, `top` / `width` бессмыслены. Любые layout-чувствительные проверки
(порядок элементов по DOM ≠ ок, нужна реальная позиция; overflow; line-clamp;
sticky) — только Playwright e2e в `frontend/e2e/`. Это записано и в моей
auto-memory как `feedback_visual_layout_testing`.

### 5. Миграции и Seed запускаются автоматически при старте backend

Не нужно отдельно `migrate up`. Логи backend покажут `migrations applied` и
`genres dictionary seeded entries=322` сразу после healthcheck. Если seed не
сработал — справочник пустой и фронт покажет коды жанров вместо имён
(fallback не молчит, видно сразу).

### 6. Каждая миграция — новый номер, прошедшие не править in-place

Текущая верхняя миграция и что добавила каждая — `docs/assistant/migrations.md`. Backend хранит applied version в
`schema_migrations` (golang-migrate), править уже-применённые .sql имеет смысл только
до push'а.

⚠️ **Номер миграции — на момент МЕРЖА, не создания ветки.** Параллельные ветки (разные
сессии) легко берут один и тот же номер (так 2026-09-26 столкнулись `0039_author_events`
и хэш сессий). Кто мержится вторым — перенумеровывается ДО мержа: golang-migrate на проде,
уже стоящем на N, миграцию с меньшим номером молча пропустит. Разовое преобразование
данных без смены схемы — не миграция, а идемпотентный шаг на старте backend (пример —
`auth.HashLegacySessionTokens`).

### 7. PR'ы идут через CI + watcher, merge только когда зелёное

User'ский флоу: `gh pr create` → армировать Monitor (`gh pr view --json
state,mergedAt` + `gh pr checks`) → дождаться `[pr] MERGED`. Это записано в
auto-memory как `feedback_pr_lifecycle_watcher`. Не объявлять задачу
выполненной только потому что CI зелёный — merge ≠ pass.

**Кто мержит (правило владельца с 2026-09-28):** на зелёном CI ассистент сам мержит
PR и выпускает **минорные (1.x.0) и фикс-релизы (1.x.y)** — включая UI-изменения.
Ждать одобрения владельца: по фичам, где он сам попросил подождать, и для
**мажорного** релиза (ломающее изменение — см. semver-контракт ниже). См. auto-memory
`feedback_pr_merge_autonomy`.

⚠️ `gh pr checks` сразу после `gh pr create` / force-push может вернуть
`no checks reported` — это значит CI ещё **не зарегистрировался**, а НЕ что
проверок нет / они зелёные. Подождать и перепроверить (дождаться событий
watcher'а), не мержить по этому статусу. (Один раз так чуть не смержили вслепую.)

**⚠️ Канонический шаблон вотчера — выстрадан (2026-07-19, «#225 давно ready,
а вотчер молчал»). Два бага, которые НЕЛЬЗЯ повторять:**
1. **Молчание на успехе.** Вотчер, эмитящий события только на MERGED/CLOSED/FAIL,
   не скажет «CI зелёный, ready to merge» — а это ГЛАВНОЕ actionable-событие
   (пользователь ждёт его для ревью/мержа). Событие — на КАЖДОЕ терминальное
   состояние: all-pass (один раз!), fail, merged, closed.
2. **Битый парсинг `gh pr checks | awk '{print $2}'`.** Имена чеков содержат
   пробелы («backend (1.25)») → $2 при дефолтном FS — кусок имени, не статус.
   ТОЛЬКО `--json`: `gh pr view N --json state,statusCheckRollup`.

```bash
# Monitor (persistent): события — READY (все чеки зелёные, один раз) / CI FAIL / MERGED / CLOSED
ready_said=""
while true; do
  j=$(gh pr view $PR --json state,statusCheckRollup 2>/dev/null) || { sleep 60; continue; }
  st=$(echo "$j" | python3 -c "import json,sys; print(json.load(sys.stdin)['state'])")
  [ "$st" = "MERGED" ] && { echo "[pr$PR] MERGED"; break; }
  [ "$st" = "CLOSED" ] && { echo "[pr$PR] CLOSED без merge"; break; }
  concl=$(echo "$j" | python3 -c "import json,sys; print(' '.join((c.get('conclusion') or c.get('status') or '?') for c in json.load(sys.stdin)['statusCheckRollup']))")
  case "$concl" in
    *FAILURE*|*ERROR*) echo "[pr$PR] CI FAIL: $concl"; break ;;
    *) if [ -z "$ready_said" ] && [ -n "$concl" ] && ! echo "$concl" | grep -qE "IN_PROGRESS|QUEUED|PENDING|\?"; then
         echo "[pr$PR] CI ЗЕЛЁНЫЙ — ready to merge"; ready_said=1
       fi ;;
  esac
  sleep 60
done
```
Смежные хронические грабли вотчеров: переменную НЕ называть `status` (zsh
read-only → молчаливый exit 1); `docker logs -f` умирает вместе с контейнером
при деплое/рестарте — прод-вотчер логов оборачивать в reconnect-цикл или
переармировать после каждого деплоя.

**Документация при КАЖДОМ PR** (явное правило пользователя, 2026-07-03): перед
`gh pr create` проверить, не требует ли содержимое PR правок в **README.md** —
он для внешнего пользователя (фичи, env-переменные, деплой/compose, внешние API
и их лимиты, безопасность). Практически любой фичевый PR = строчка в
«Возможностях»; новый env — строка в env reference; смена портов/образов —
секции деплоя (⚠️ и `docker-compose.no-caddy.override.yml` — про него забыли
при переходе фронта на nginx-unprivileged:8080, no-caddy деплой молча сломался
до docs-ревизии 2026-07-03). Это ДОПОЛНЯЕТ правило про актуализацию CLAUDE.md
(auto-memory `feedback_keep_claude_md_current`): CLAUDE.md — для ассистента,
README — для пользователя, проверяются ОБА.

**Semver-контракт: ломающее изменение = новый мажор (правило владельца, 2026-09-25).**
Публичный (DMZ) инстанс сидит на движущемся теге `1` и **сам** обновляется раз в неделю
(`docker compose pull && up -d` по таймеру, без человека). Поэтому всё, что при обновлении требует
ручного действия или ломает существующий деплой, выпускается ТОЛЬКО следующим мажором (`2.0.0`),
не минором/патчем. **Ломающее:** удалён/переименован env или его семантика/дефолт изменились так,
что старый `.env` работает иначе; нужна правка compose/Caddyfile/`.env`/томов; смена мажора
PostgreSQL/Meilisearch (дамп/миграция данных); миграция БД, которая не применяется сама на старте
или требует ручных шагов; удалён/несовместимо изменён внешний интерфейс (URL OPDS, `/api/*` для
внешних клиентов); выросли минимальные требования к хосту. **НЕ ломающее:** новые фичи, новые env
с безопасным дефолтом, обычные авто-миграции и ресинки индексов на старте (даже тяжёлые — но
отметить в release notes). Сомневаешься — считай ломающим и спроси владельца. В PR с ломающим
изменением — пометка `BREAKING` и что сделать при обновлении. `infra/.env.public.example` держит
`SKRIPTES_VERSION=1` — при релизе его НЕ бампать.

**Релиз:** бамп `SKRIPTES_VERSION` в `infra/.env.example` + `README.md` → PR →
merge → аннотированный тег `vX.Y.Z` (identity-флаги, см. ниже) → `release.yml`
собирает multi-arch образы в ghcr. Moving-теги `latest` / `{major}.{minor}` /
`{major}` ставятся ТОЛЬКО на stable (без `-` в теге); пре-релизы `-beta` их не
трогают. Текущая версия и история релизов — `docs/assistant/release-history.md`.

### 8. Не выдумывать семантику данных

Если в `.inp`-записи попадается неизвестный маркер (например, цифра в поле
`DEL` помимо 0/1, новое поле в `structure.info`, неожиданное значение `EXT`) —
не гадать, что оно значит. Записать defensive-обработку с явным fallback'ом и
TODO «уточнить у пользователя / в спеке». Это `feedback_no_invented_semantics`
в моей auto-memory.

### 9. Чёрно-белая тема — цвет только в контенте

UI монохромный; цвет появляется только в контенте (обложки, фото). Подсказки и
предупреждения — НЕ цветом, а монохромным `callout` (рамка + `bg-muted` +
иконка): `frontend/src/components/ui/callout.tsx`. Не вводить `text-amber/yellow`
и т.п. в UI (исключение — семантический `text-destructive` для ошибок).

### 10. Контролы и типографика

- Мгновенное вкл/выкл → `ui/switch.tsx` (применяется сразу). Checkbox в наших
  разделах = «отметь, потом Сохрани кнопкой» — не путать семантику.
- Контекстозависимое сохранение формы (бар «Есть несохранённые изменения»,
  появляется при изменениях) → общий `frontend/src/components/SaveBar.tsx`.
- Висячее слово на последней строке абзаца (orphan) лечится `text-pretty`
  (Tailwind `text-wrap: pretty`), а не переформулировкой.

### 11. Кэш картинок — три РАЗНЫХ бакета, не путать жизненный цикл

`/cache/covers` (обложки книг), `/cache/posters` (постеры экранизаций),
`/cache/author-photos` (фото авторов) — отдельные каталоги + отдельные
`CoverCache` (свои бюджеты), пути выводятся как соседние к `coverRoot` в
`metadata.New`. Обложки книг **регенерируются** из fb2 (`ServeCoverByID` сам
переизвлекает) → их LRU-эвиктит и сносит «Очистить кэш обложек». Постеры/фото —
**внешний источник, НЕ регенерируются**: свои кнопки очистки
(`/clear-posters`/`/clear-photos`, зануляют `poster_path`/`photo_path` чтобы не
осталось битых `?`) и бюджеты (дефолт 0 = без эвикции). Раздавать всё —
`GET /api/covers/{name}` через `Enricher.ResolveCachedFile` (ищет по трём дирам).
Висячие указатели (файл удалён, ссылка осталась) лечит `Enricher.HealDanglingAssets`
на старте: зануляет + сбрасывает маркер попытки (`adaptations_fetched_at`/
`metadata_fetched_at`), чтобы дозаполнение перекачало. Не клади постеры/фото в
`coverRoot` — их снесёт эвикция обложек.

**Что считается экранизацией (#295).** P144 «основано на» есть и у опер, видеоигр, песен,
настольных игр — на проде 37 % записей были такими. Вид — по ВСЕМ меткам P31 сущности
(`screenKind`: у фильма меток несколько, и первая бывает «произведение искусства»;
приоритет мини-сериал > аниме > сериал > фильм; `mapWikidataKind` — белый список: кино,
телефильм, телеспектакль, мультфильм, сериал, веб-сериал, мультсериал, мини-сериал, аниме).
`kindOther` и записи с голым QID вместо названия не сохраняются; подписи — на
`ru,en,mul,uk,de,fr,es,it,ja`. Старые записи разово вычистил
`metadata.CleanupNonScreenAdaptations` (гейт `adaptations_screen_only_v1`): книги, где среди
удалённого мог быть настоящий фильм (у «другого» ссылка на Кинопоиск/IMDb, или запись без
названия), получили сброшенный `adaptations_fetched_at` — перепросятся.

**Постеры экранизаций — источник TMDB (приоритет) → Commons P18 (фолбэк).**
Wikidata-P18 у фильмов почти пуст (постеры копирайтные; на реальном проде
покрытие было ~16%, у «Разум и чувства»/«Ёжика» — ноль). TMDB-id приходит
БЕСПЛАТНО из того же SPARQL-ответа адаптаций (P4947 фильм / P4983 сериал) —
поиска по названию нет, ложных матчей нет; `metadata/tmdb.go::TMDBPosterProvider`
(GET /3/movie|tv/{id} → poster_path → image.tmdb.org/t/p/w342, ключ env
`SKRIPTES_TMDB_API_KEY` — принимается И v3 «API Key», И v4 «Read Access
Token» eyJ… (автодетект по префиксу: Bearer vs query); без ключа TMDB 401,
работает только P18; ключ пробрасывают ОБА compose, атрибуция TMDB — в
README). Тумблер источника в админке («Экранизации» → «Источники постеров»,
`BioAdaptationConfig.TMDBPosters`, дефолт вкл) → `Enricher.SetTMDBPostersEnabled`
без рестарта: выключен — как без ключа (только P18, `RecheckPosterHoles` no-op);
ответ настроек несёт `tmdb_configured` (без ключа UI тумблер выключает). PUT
настроек ложится поверх сохранённого конфига — клиент без поля его не сбрасывает. **Собственный rate-кламп `tmdbRPM=600` (10 req/s) в провайдере**
(зеркало clampOLRPM, из админки не задирается): гейт проходят ВСЕ пути —
воркер, lazy, перепроверка — RPM воркера «Экранизации» его не обходит. Провязка:
`enricher.resolvePosterURL` (TMDB → P18) в `saveAdaptations`. Три защиты от
необратимой потери постеров (все три были багами): (1) `saveAdaptations` НЕ
ставит `adaptations_fetched_at`, если постер-источники были, а ни одно
скачивание не удалось (транзиент: 429/сеть/ErrCacheFull) — строки пишутся,
книга остаётся pending, следующий заход дозальёт через ON CONFLICT COALESCE;
(2) «Очистить постеры» (`ClearPosterCache`) теперь сбрасывает и маркер у книг
с экранизациями — семантика «очистить и перекачать», раньше была необратимая
потеря (воркер берёт только NULL-маркер); (3) админ-кнопка **«Дозаполнить
постеры»** (`RefillMissingPosters`, POST
`/admin/adaptation-enrichment/refill-posters`) — сброс маркера ТОЛЬКО у книг с
постер-дырами → воркер «Экранизации»/lazy перепройдёт и дозальёт (жать после
включения TMDB-ключа на существующей коллекции — разовый бутстрап, заодно
персистит TMDB-id старым строкам). **Авто-перепроверка постер-дыр** (миграция
0037): TMDB-id (`tmdb_movie_id`/`tmdb_tv_id`) персистятся при записи адаптации
→ фаза `RecheckPosterHoles` воркера «Экранизации» (каждый 30-мин цикл, батч
500) перепроверяет дыры чистым TMDB-вызовом БЕЗ SPARQL с поштучным TTL
`poster_checked_at` (7 дней, `posterRecheckTTL`) — постер совсем нового фильма
(«честный ErrNotFound» в момент первого фетча) появится сам, без кнопки.
Found → дыра закрыта; всё ещё нет → следующая проверка через TTL; транзиент →
checked_at не трогается (ретрай в следующем цикле). Без TMDB-ключа фаза no-op.
⚠️ Остаточная staleness: НОВЫЕ экранизации у уже-фетченных книг single-shot
маркер не увидит (TTL-перекраул самих адаптаций — follow-up, SPARQL-бюджет).

### 12. Lazy-обогащение автора — single-shot по `metadata_fetched_at`

Био/фото автора тянутся лениво при открытии карточки. Чтобы не долбить
Wikipedia/OL на каждый заход у авторов без биографии: `EnsureAuthorBio` ставит
`metadata_fetched_at` и на промахе, `triggerAuthorEnrichmentAsync` пропускает,
если `EnrichmentFetched`, фронт (`useAuthor`) прекращает поллинг и показывает
fallback по `enrichment_fetched`. Тот же принцип у экранизаций
(`adaptations_fetched_at`). Хочешь ретрай — нужен отдельный TTL-механизм.

### 13. Матчинг автора во внешних — гейт по имени (анти-false-positive)

Поиск автора по имени даёт однофамильцев («Гарднер Лиза» → «Иван Гарднер»).
`metadata/authormatch.go::authorNameMatches` принимает кандидата, только если
совпадают И фамилия, И имя (транслитерация Cyrillic↔Latin, Левенштейн ≤1).
Встроен в `WikipediaProvider.resolveTitle` (bio+photo) и
`OpenLibraryProvider.authorSearch`. Поиск статьи — `resolveByName`: формы «Фамилия Имя Отчество», «Фамилия Имя»,
«Имя Фамилия» (псевдонимы, китайские имена), до 5 результатов на форму. Несколько статей прошли гейт имени: страницы «(значения)» не в счёт; ровно одна без уточнения — основная (по соглашению Википедии главный носитель имени: «Тургенев, Иван Сергеевич» при «… (учёный)»), а если политика её отвергла — строгий путь; несколько без уточнения — тёзки, строгий путь (слой 3). ⚠️ Урок 1.19.0: без этого Достоевский, Тургенев, Пушкин уходили на строгий путь, и перепроверка очистила био Достоевского — приёмка правок поиска только с прогоном по самым известным авторам. Редирект с имени на статью под другим именем принимается, если полный текст статьи называет
автора (`redirectNamesAuthor`, псевдоним «Йовил» → «Ньюман»). Английская Википедия и OpenLibrary ищут по
латинскому имени из fb2 переводов (`AuthorQuery.LatinName`/`latinQuery`, голосование книг без сборников). Фамилия и имя из нескольких частей («Ле Гуин», «Гарсиа Маркес»,
«Жан-Кристоф») сверяются по частям, частицы (де, ле, ван, фон…) необязательны, из поля имени берётся
первое слово (`requiredParts`, #348; раньше часть склеивалась в один токен и такие авторы не совпадали никогда).
Сбой источника (429/сеть) останавливает цепочку провайдеров: решение откладывается, нижний источник
(OpenLibrary) не спрашиваем — иначе 429 Википедии отдавал решение ему, и перепроверка меняла верную био
на чужую (#347; `fetchAuthorBio`/`fetchAuthorPhoto`, `EnsureAuthorBio`/`EnsureAuthorPhoto`, сухой прогон). Философия — **precision > recall**: лучше
пустая карточка, чем чужие био/фото. Левенштейн ≤1 — ТОЛЬКО между разными алфавитами
(транслитерация: Лиза≈Lisa); кириллица с кириллицей — точно («Фирсов»≠«Фурсов», #280), кроме разных
передач одной иностранной фамилии (`transcriptionKey`: удвоенные буквы Флевеллинг=Флевелинг, H как Г/Х
Херберт=Герберт, S как З/С Зузак=Зусак; гласные — нет) и, только для ИМЕНИ, одной вставленной/пропущенной
буквы (Фритц=Фриц, Наталия=Наталья; у фамилий так совпали бы Юрмин/Юрин). Проверка профессии (P106) принимает, кроме
писателей, и тех, кто пишет нехудожественные книги (учёные, исследователи, преподаватели вузов,
историки, философы, журналисты, переводчики, критики, редакторы, юристы — `writerBaseClasses`):
иначе отвергала математика Гутера и историка Каткова. Редирект на статью под другим именем годится
(`articleIsAuthor`), если автора называет начало статьи — полное имя героя, в том числе латиницей
(«Матесон Ричард» → «Мэтисон, Ричард», «Richard Burton Matheson»), или статья называет настоящее имя
(`mentionsAuthor`: «Акунин, Борис» — «настоящее имя — Чхартишвили»).
В строгом пути имя сверяется с основой названия статьи, без уточнения («Старый пруд (Басё)» — не Басё).
Имя из одного слова («София», «2B») — строгий путь, как у тёзок (`AuthorQuery.Strict`,
подтверждение книгой). В пути био (`intro`) и фото (`summary`) страница неоднозначности
(`pageprops.disambiguation`) не берётся: по имени нашлась неоднозначность — у автора есть тёзки,
поиск повторяется строгим путём (`asNamesake`: «Дюма, Александр» → книга «Три мушкетёра» →
«Дюма, Александр (отец)»); редирект на другое имя отсекает гейт по итоговой статье. Сбой Википедии или проверки профессии → `ErrUpstream` (перепроверка позже,
грабля №20), а не «не найдено» и не «принять». Уже скачанные био/фото перепроверяет фоновый
`metadata.AuthorRechecker` (`runAuthorMetaRecheck` в main, состояние `author_meta_recheck_v4` в
app_settings — бампнуть версию, чтобы перепроверить заново после новых гейтов): v3 (`WithAllAuthors`) — все
авторы с книгами, кроме служебных (~140 тыс., ~3,5 суток; v1/v2 шли только по авторам с био или фото
и тем, у кого прошлая перепроверка что-то очистила),
от известных к неизвестным, с RPM воркера био; то же — не трогаем, другое — заменяем, гейты не
пропускают — очищаем, сбой — повтор через 30 мин; изменения с прежними значениями — в журнале
`author_meta_recheck` (миграция 0043, для отката). Прежние файлы фото не удаляются.

**Трасса решений (разбор ошибок, #280).** Провайдеры авторов (Википедия, строгий путь тёзок, OpenLibrary)
и проверка профессии пишут шаги в трассу из контекста (`metadata/trace.go`: `WithAuthorTrace`, `traceStep`;
исходы pass / reject / error / info, этапы opensearch, name_gate, strict.*, qid, occupation, disambiguation,
article_is_author, extract, thumbnail, accept). Без трассы в контексте шаги ничего не стоят. Wikidata при
включённой трассе отдельным запросом пишет названия профессий кандидата («*» — засчитана пишущей).
Перепроверка пишет короткую причину (`AuthorTrace.Reason()`: решающий шаг по каждому источнику и языку) в
`author_meta_recheck.reason` (миграция 0044). Сухой прогон — бинарник `skriptes-explain`
(`cmd/skriptes-explain`, `Enricher.ExplainAuthor`): id из stdin → строка JSON с решением, началом био, адресом
фото и трассой; базу не трогает, фото не скачивает (`AuthorPhotoSource` у обоих провайдеров). Разбор ошибок
и перепрогон с нуля — план `~/projects/plans/skriptes/archive/author-bio-case-study-plan.md`.

**Слой 2 — политика приёма кандидата** (`metadata/candidate_policy.go`, case study #280, отчёт
`~/projects/plans/skriptes/archive/author-bio-case-study-report.md`; планка владельца — ≈5 % чужих среди принятых).
Прежний гейт смотрел только на профессию P106 (не писатель — отказ, остальное — приём) и давал 12,5 % чужих:
смежные профессии (учёный, журналист, юрист) и кандидаты без P106 проходили без вопросов, а генералы и политики
с мемуарами отвергались. Теперь после гейта имени провайдер (`WikipediaProvider.resolveTitle`,
`OpenLibraryProvider.authorSearch`) зовёт `CandidateCheck` (`WithCandidateCheck`, в main —
`NewCandidateCheck(wdAdaptations.CandidateFacts)`): факты Wikidata — `CandidateFacts` (метки профессий и годы;
классы профессий обходом P279*: writer/author — писатель, остальные `writerBaseClasses` — смежная; работы с
автором P50) — три лёгких SPARQL (совмещённый с сервисом подписей WDQS не успевал). Профиль книг автора
(`MinBookYear`, `NetShare` — доля сетевой литературы, `Genres`) грузит `withNamesakeContext`. Порядок
`decideCandidate`: кандидат не человек (P31 ≠ Q5: статья о сериале или цикле, найденная строгим путём по книге) → отвергнуть; строгий путь подтвердил или книга автора среди работ P50 → принять; нестрогое имя (`looseNameMatches`, `MatchLoose`: Ширли/Шерли, Гуидо/Гвидо — другая передача иностранного имени; так же совпали бы Фирсов/Фурсов) — только с книгой P50; однословное имя без уточнения — статья с точным названием (`strict.exact_title`, «Тукарам», «Алкуин») как обычный кандидат; кандидат родился позже книг
(−12), умер до 2000 при сетевой литературе, у автора > ½ сетевой литературы, в названии статьи другое отчество →
отвергнуть; писатель → принять; смежная или нет P106 → только с подтверждением (отчество совпало или тема книг ↔
профессия, `topicRules`); не писатель → тема ↔ профессия, эпоха сходится, отчество совпало или его нет. Решение и
профессии — в трассе (шаги `occupation`, `policy`). Сбой Wikidata → `ErrUpstream` (перепроверка позже).
Проверено и отвергнуто (см. отчёт): «умер до года книги» (посмертные издания классиков), язык письма P1412.

**Слой 3 (реализован) — тёзки, `AuthorQuery.Strict()`** (есть `name_note` или в базе другой автор с
тем же именем, грабля №22). Первый результат поиска по имени здесь — просто самый известный из
тёзок, поэтому кандидат принимается только с подтверждением (`metadata/namesake.go`):
Википедия — статья «ФИО (уточнение)» (`wikiTitleBases` + `articleTitle`; ruwiki различает тёзок
так же: «Антоний (Блум)») → кандидат opensearch, чьё уточнение совпало по основе
(`noteMatchesQualifier`: «писатель-маринист» ~ «(писатель)») → полнотекстовый поиск «фамилия» +
«название книги» (`searchText`); OpenLibrary — только якорь по книгам (`strictAuthorKey`: автор
книги с нашим названием, прошедший имя-гейт). Контекст (уточнение, признак тёзок, до 6 названий
книг — свои и `src_title`) `Enricher.withNamesakeContext` подтягивает сам по ID. Номера `#NNN` во
внешних источниках не ищем. Не подтвердилось — `ErrNotFound`.

**Строгий путь по работам Wikidata (#410) и словарь имён (#259).** Если ни статья с уточнением, ни
полнотекстовый поиск книгу не подтвердили, строгий путь Википедии ищет кандидатов-однофамильцев и
сверяет их работы в Wikidata (P50, `?wLabel`/P1476, до `strictWorksCandidates`=5 кандидатов) с
названиями книг (`strictByWorks` в `namesake.go`): в приёмке так нашлись «Артур, Роберт (драматург)», «Мэдисон,
Джеймс» по «Федералисту», «Смит, Джозеф» по «Книге Мормона», Вильгельм Буш, Мануэль Ривас — полнотекст их не
подтверждал. Факты кандидата кэшируются один раз на процесс (`CachedCandidateFacts` —
общий кэш для политики и строгого пути, `WikipediaProvider.WithCandidateFacts`). Латинское имя без
переводов (`AuthorQuery.LatinName` пусто) угадывается: имя — по словарю устойчивых передач
(`name_equivalents.go`, ~120 русских имён → латинские варианты; «Джон» ↔ John — и для гейта имени в обе
стороны, `firstNameEquivalentMatches`), фамилия — транслитом. Угаданное имя помечается
`LatinGuessed`: **OpenLibrary принимает такого кандидата только по книге** (`strictAuthorKey`, как у
тёзок) — по угаданному «John Holm» нашёлся драматург John Cecil Holm вместо псевдонима соавтора
Гаррисона. Приёмка 2026-10-07 (1448 авторов: 1000 самых известных, 168 очищенных перепроверкой v4, 300
переводных без латинского имени и био): био — 824 без изменений, 18 настоящих находок (17 верных,
неверная исправлена `LatinGuessed`), 0 настоящих потерь (15 «пропаж» — сбои SPARQL в сухом прогоне,
в воркере это повтор), фото — 14 находок, 0 потерь; доля сбоев SPARQL та же, что у прод-версии.
Перепроверку (v5) для уже обогащённых авторов этот выпуск не запускает.

### 14. Коды языка нормализуются (lower+trim); видимость контента — и в каталоге

Два связанных правила про язык/видимость:

1. **Нормализация `lang`.** В INPX/fb2 один язык приходит в разном регистре
   (`ru`/`RU`) и с локалями (`ru-RU`, `en_US`), из-за чего он двоился в списке
   языков/фильтре/видимости (скрыть надо было каждый вариант отдельно). Импорт
   нормализует код: `importer.normalizeLang` = lower + trim + срез регионального/
   скриптового субтега (`ru-RU`/`zh-Hans`→`ru`/`zh`) в `processRecord` → PG и Meili.
   Существующие данные чинят миграции `0015` (lower+trim) и `0016` (срез субтега), а
   Meili-индекс — разовый `Importer.ResyncLangs` на старте (гейт
   `app_settings.lang_normalized_vN`, см. `cmd/skriptes/main.go::runOnceLangResync`;
   ключ бампается при смене правил нормализации, чтобы Meili пересинкнулся).
   `catalog.ListLanguages` тоже группирует по `lower(btrim(lang))` (defensive-дедуп).
   Новый код, кладущий `lang`, обязан нормализовать. `src_lang` из fb2 грязнее
   (ISO 639-2, коды стран, слова «английски») — его пишет только
   `langcode.Canonical` (таблица ISO 639-1 + алиасы; нераспознанное → не пишем).

2. **Видимость контента течёт в каталог, если не фильтровать.** `/books` режет
   скрытые жанры/языки Meili-фильтром, но карточки автора/серии — отдельные
   PG-запросы. `catalog.GetAuthor`/`GetSeries` принимают `excludeGenres/excludeLangs`
   (из `ContentResolver.Exclusions`, прокинуты хендлерами) и добавляют
   `bookExclusionClause` к спискам книг и счётчику. Добавляешь новый список книг
   (где угодно) — прогоняй через те же исключения, иначе скрытый контент всплывёт.

### 15. Книга (Work) vs издание (fb2-файл) — переход к FRBR, идёт по фазам

Большой рефактор: логическая **книга** (`works`) над физическими **изданиями**
(строка `books` = один fb2-файл). План — `~/projects/plans/skriptes/archive/works-editions-frbr-plan.md`.
**Phase 1 (сделано) — только фундамент данных, read-path'ы НЕ тронуты:**
- Миграция `0017_works`: таблица `works` (Work-level поля: каноническое
  название, primary_author_id, written_year, series_id/ser_no, ext_ids,
  edition_count) + `books.work_id` FK. Бэкфилл сделал каждую существующую книгу
  **singleton-работой**. Инвариант: у каждой книги есть `work_id`, у каждого
  Work ≥1 издание. Импортёр (`importer/upsert.go::ensureSingletonWork`) держит
  инвариант для новых книг (своя работа на каждую; группировку НЕ делает).
- Миграция `0018_edition_fields`: edition-поля на `books` — `translator`,

  для back-compat API. ⚠️ books-индекс (OPDS) popularity по-прежнему 0 — там вторично.
- **Ресинк works-индекса** (`importer/importer.go`): `ResyncWorksIndex` (полный
  upsert всех живых работ, батчи по id, UNION авторов/жанров/языков подзапросами,
  year = COALESCE(work.written_year, min года изданий)), `UpsertWorksToIndex(ids)` /
  `DeleteWorksFromIndex(ids)` (таргетно). Точки синка: импорт (полный, в конце Run),
  старт (`runOnceWorksIndexSync`, гейт `works_index_synced_v<схема>` — при бампе схемы
  `RebuildWorksIndex`: сборка во временном `works_rebuild` + swap, поиск работает всё время,
  изменения за время сборки досылаются по `works.updated_at`; + `ConfigureWorksIndex`
  на КАЖДОМ старте), группировка (`work_grouper` копит touched/deleted → таргетный
  синк через type-assert `WorksIndexSyncer`; GC работ = `DELETE ... RETURNING`),
  год (`year_backfill` drain post-pass — таргетный upsert изменённых работ; ленивый
  `EnrichBooksNow` works НЕ трогает — наполнится на следующем полном ресинке),
  ручные split/merge (`syncSearchAfterManual` — детачнуто: ResyncWorkIDs + works-синк).
- **Сверка индексов с PG** (`importer.ReconcileIndexes`, #283): на каждом старте и в конце импорта id документов Meili (works и books) сравниваются с живыми записями PG — лишние удаляются (документы удалённых импортом книг, опустевших/слитых работ, потерянные остановкой синки группировки #270), недостающие работы досинкиваются (в том числе весь works-индекс, если Meili пуст после восстановления базы). Предохранители: пустой PG или «лишних» больше половины — удаление отменяется. Ресинки только добавляют/обновляют — удаление держится на сверке. Индекс книг (OPDS) пишет только импорт: если в нём нет ≥10% живых книг (база восстановлена из дампа на пустой Meili, #305), старт сбрасывает `last_inpx_hash` — стартовый импорт идёт полностью (`ReconcileResult.BooksNeedReimport`).
- **Веб-путь** (`books/service.go`): `ListWorks`/`SuggestWorks` (индекс `works`,
  id = works.id, обложка+`cover_edition_id`+`edition_count` гидрируются по work_id),
  `GetWork(workID, excl)` = выбрать ВИДИМОЕ представительное издание → `Get(repID)`.
  `handleListBooks`→`ListWorks`, `handleSuggest`→`SuggestWorks` (+ work-level
  is_favorite через `history.FavoriteWorkSet`). OPDS остаётся на `List`/`Suggest`.
- **Скрытие контента на works**: genres — `NOT IN` (жанры уровня работы); язык —
  `lang IN [видимые]` (видимые = вселенная−скрытые, кэш `allLangs` 5 мин), т.е.
  работа видна, если есть издание на видимом языке (мультиязычную работу не прячем
  целиком из-за одного скрытого языка). Вселенная неизвестна → fallback `NOT IN`.
  ⚠️ **Внутри карточки скрытые языки тоже режутся**: `GetWork` после `Get(repID)`
  прогоняет `Editions` через `visibleEditions(editions, excludeLangs)` — издания на
  скрытом языке не показываются даже сгруппированные в видимую работу (счётчик
  секции = `editions.length`, консистентен сам). Открытое издание repID — видимое
  по построению `visibleWorkEditionID`. Back-compat `/books/{id}` (`handleGetBook`→
  `Get` без exclusions) НЕ фильтрует — вторично, туда ходят только прямые старые
  ссылки; discovery-ссылки идут на `/works/{id}`.
- **Маршрут `/works/{id}`** (основной для карточки): `api/works.go`-нет, ручка
  `handleGetWork` в `api/books.go` (общий хелпер `writeBookCard` с `handleGetBook`);
  router `/works/{id}` без bookGate (видимость решает `GetWork`→404). `/books/{id}`
  остаётся (back-compat: прямые ссылки, возврат из ридера). Фронт: `router.tsx`
  `/works/$id`→`<BookDetailPage mode="work">` (`useBookCard(id,mode)`/`useWork`);
  discovery-ссылки (`BookListItem`, `BooksPage`, `CommandPalette`) → `/works/{work_id ?? id}`
  (catalog кладёт `ListItem.WorkID`, т.к. там ID = издание; в works-выдаче ID и так
  = works.id). Ридер/скачивание/«Читать» — по-прежнему `/books/{editionId}`.
- ⚠️ id работ и изданий ПЕРЕСЕКАЮТСЯ (отдельные sequence) → `/books/{N}` ≠
  `/works/{N}`; поэтому работа-URL — отдельный маршрут, не «трактовать books id как work».
- **`works.title` локализован на язык библиотеки** (`metadata/work_title.go`): при
  слиянии «оригинал+перевод» каноникой могло стать иноязычное издание → заголовок
  карточки (`COALESCE(w.title,b.title)`) и works-индекс были английскими при русских
  изданиях (рассинхрон со списком `b.title` представителя + провал поиска по рус.
  названию). `recomputeWorkTitles` переписывает `works.title`/`normalized_title` на
  издание в `dominantLang` (самый частый язык коллекции) — ТОЛЬКО если такое издание
  есть (иноязычную-без-перевода работу не трогаем). Из изданий на этом языке — САМОЕ
  ЧАСТОЕ название (без различия ё/е; при равенстве — текущее, чтобы не прыгало), а не
  «новейшее с обложкой» (было «Собрание сочинений в 2 томах. Том 2. Золотой теленок»
  при семи «Золотых телятах», #306); у переименованных разовым проходом работ
  эвристический тип пересчитывается (`ReclassifyWorkKinds`). Работа из одного
  издания на ЛЮБОМ языке — название этого издания (`syncSingletonWorkTitles`). Тот же
  `LocalizeWorkTitles` зовут шаги после импорта: импорт переписывает название издания,
  но не работы («Big Money» при единственном издании «Дневники 1939-1945», #285). Точки: группировка `apply` +
  ручные merge/split (затронутые работы → в touchedWorks → таргетный ресинк индекса);
  разовый backfill `runOnceWorkTitleLocalize` (гейт `app_settings.work_title_localized_v3`,
  ПОСЛЕ `runOnceWorksIndexSync`) + `UpsertWorksToIndex(changed)`. Представитель карточки
  `books.visibleWorkEditionID` предпочитает издание-якорь (`normalized_title ==
  works.normalized_title`) → обложка/lang/скачивание совпадают с локализованным title.

### 16. ★-избранное книг — это служебная полка, таблицы `favorites` БОЛЬШЕ НЕТ

После унификации (PR #109, миграция `0023`) книжное «избранное» = членство в
служебной коллекции `user_collections.kind='favorites'` (одна на юзера через
partial unique `user_collections_one_fav`). ★ на книге — её one-click шорткат.
Таблица `favorites` **дропнута** — не ищи её, не пиши в неё. Книжный API не
менялся (`POST/DELETE /api/books/{id}/favorite`, поле `is_favorite`); репойнт
только внутри бэка — все читают/пишут favorites-коллекцию:
- `history/service.go` — `AddFavorite` (CTE: ensure favorites-полки + membership),
  `RemoveFavorite`/`IsFavorite`/`IsWorkFavorite`/`FavoriteWorkSet`/`ListFavorites`/
  `FavoritesCount`; `history/persona.go` — источник `FavoriteBooks` для re-ranking;
  `catalog/authors_list.go` — счётчик `fav_books` на `/authors`.
- Служебную полку нельзя переименовать/удалить/создать-дубль:
  `collections.ErrSystemCollection`/`ErrReservedName` → 400 (`api/collections.go`).
  `ListCollections` отдаёт `kind` и закрепляет favorites ПЕРВОЙ.
- Фронт: `Collection.kind`/`BookShelf.kind` (`lib/collections.ts`); ★↔полки
  держат синхронными кросс-инвалидацией (`invalidateFavoriteSide` + `['me','collections']`
  в `useToggleFavorite`). На карточке книги `ShelfSection` исключает favorites из
  чипов «На полках» (её передаёт ★). `/shelves` — favorites закреплена, без удаления.

⚠️ **Авторы/серии — это ПОДПИСКА, не «избранное»** (питает «Новинки по подпискам»;
свои таблицы `favorite_authors`/`favorite_series` — НЕ трогались). Иконка у них —
колокольчик (`Bell`, монохром), а не звезда: `FavoriteButton` (`target!=='book'`),
suggest `FavoriteMark`, hero-дропдаун (`HomePage`), строка автора (`AuthorsPage`).
Книжная ★ — жёлтая звезда (исключение из монохрома, граблю №9).

### 17. ДВА рейтинга — не путать: библиотечный (донор) vs читательский (инстанс)

После фичи оценок (1.2.0) у книги/автора ДВА разных рейтинга:
- **Внешний (НЕ читательский)** — единый «Внешний рейтинг» (иконка `Globe`), объединяет
  два источника с приоритетом показа LIBRATE → web:
  - LIBRATE (донор) — `books.rating` из INPX (рейтинг librusec/flibusta), только из импорта;
  - web — `books.external_rating`/`_source`/`_count` (Google Books/OpenLibrary), миграция
    **0026**, заполняется фоновым воркером `metadata/external_rating_backfill.go` (opt-in из
    админки «Фоновые операции», per-source выбор + охват; учёт попыток `book_external_rating_lookups`,
    миграция **0027**; из включённых источников берётся оценка с бОльшим числом голосов).
  Карточка: `BookDetailPage::externalRatingDisplay` (LIBRATE→«N · библиотека», иначе
  web→«N · Google Books»). **Веб-оценка учитывается только от 5 голосов** (#296,
  `books.MinExternalRatingVotes`/`ExternalRatingSQL` — карточка, списки, `WorkMeta`, рейтинг автора; 53 %
  веб-оценок были одноголосыми); LIBRATE — как есть (голосов у неё нет). **Рейтинг автора** (#296, миграция
  **0049** — `authors.max_rating` → `rating_score`): среднее пяти лучших работ (оценка работы — LIBRATE, иначе
  веб от 5 голосов; без сборников) с подтяжкой к 3,35 (средняя LIBRATE) у кого работ меньше
  (`catalog.RecomputeAuthorStats`, константы `ratingTopWorks`/`ratingPriorWeight`/`ratingPriorMean`): пять
  «пятёрок» → 4,53, одна → 3,9. Было `max(…)` — у 4,4 тыс. авторов «5.0», сортировка «по рейтингу» = «по числу
  книг». Список/фильтр `MinRating` (float, пороги 3,5–4,5)/sort=`rating` (ничьи — по известности)/карточка
  автора читают хранимое значение — личные скрытия в него не входят; `external_rating_source='top_works'`.
  Исследование — `~/projects/plans/skriptes/ratings-renown-research.md`.
  **Оценка Фантлаба** (миграция **0050**): тот же ответ `search-works`, что даёт воркеру «Известность» число оценок,
  несёт среднюю (`midmark`, 1–10) и сглаженный рейтинг Фантлаба (`rating`) — `writeRenown` пишет
  `works.fantlab_midmark`/`fantlab_rating`; разовый перезапрос найденного — гейт `fantlab_ratings_v1`. Карточка книги
  показывает «Фантлаб 9,1» отдельным чипом (своя шкала, не вместо «внешнего рейтинга») от `books.MinFantlabMarks`
  = 10 оценок. **В рейтинге автора Фантлаб первым** (#394): оценка работы = рейтинг Фантлаба от 10 оценок в шкале LIBRATE (`books.FantlabOnLibrateScale`/`…SQL` — кусочно-линейное квантильное соответствие на 12 тыс. работах с обеими оценками, прод 2026-10-06: 3,10→1 · 3,43→1,5 · 3,96→2,5 · 5,61→3,5 · 7,16→4,5 · 7,68→5), иначе LIBRATE, иначе веб от 5 голосов. Сравнение вариантов (Фантлаб первым / только заполняет пробелы / средняя вместо рейтинга / от 50 оценок) — в `~/projects/plans/skriptes/ratings-renown-research.md`; «Фантлаб первым»: 300 самых известных авторов — медиана места 434 вместо 1014, рейтинг у 15,3 тыс. авторов вместо 14,1 тыс., мейнстрим с малым числом оценок на Фантлабе проседает (Диккер 4,39 → 3,87). Откат на «заполняет пробелы» — порядок COALESCE в `catalog/author_stats.go`.
- **Читательский (этого инстанса)** — пользовательские оценки 1–5, work-level:

### 18. iOS PWA safe-area — СИСТЕМНО (не env() по месту); хэдер отделён тенью

`index.html`: `viewport-fit=cover` + `apple-mobile-web-app-status-bar-style=black-translucent`
⇒ в standalone-PWA на iOS контент full-bleed'ит ПОД системные бары (часы/home-indicator).
Значит **любой `fixed`/`sticky` элемент у края экрана ОБЯЗАН добавить соответствующий
safe-area-инсет**, иначе контент лезет под бар. Раньше инсет ставили `env(...)` ad-hoc
(только хэдер) → дроверы/саб-бары его не получали и ломались «в случайных местах».

Теперь паттерн **единый**: именованные утилиты `pt-safe`/`pb-safe` (`@utility` в
`src/index.css` = `padding-top/bottom: env(safe-area-inset-*)`; на десктопе/в Safari = 0).
Где применены и почему (правишь top-/bottom-anchored оверлей — добавляй так же):
- **Хэдер** (`Layout.tsx`): `pt-safe` + **тень** `shadow-[0_10px_22px_-10px_rgba(0,0,0,0.9)]`.
  Хэдер, контент и боди — ОДИН цвет `--background`, а `--border`=10% white почти невидим
  → при скролле хэдер «сливался» с контентом (юзер читал как «прозрачный»; на деле
  `bg-background` сплошной). Тень даёт глубину — хэдер читается как слой над контентом
  (box-shadow на iOS Safari надёжен, в отличие от backdrop-blur). z-20 (выше саб-баров).
- **Sheet-дроверы** (`ui/sheet.tsx`, ВСЕ usage — nav/мобильные фильтры): `pt-safe pb-safe`
  на боковых (во всю высоту), `pt-safe`/`pb-safe` на верх/низ; close-кнопка
  `top-[calc(env(safe-area-inset-top)+0.75rem)]` (absolute, иначе под баром).
- **Sticky-саб-бары фильтров** (`AuthorsPage`/`BooksPage`): липнут ПОД хэдером →
  `top-[calc(env(safe-area-inset-top)+3.5rem)]` (инсет + высота хэдера h-14). На `top-14`
  уезжали бы ПОД хэдер (который на iOS выше на инсет) и пропадали.
- **Нижний баннер установки** (`InstallPromptBanner`): `pb-safe`.
- **CommandPalette** (`components/CommandPalette.tsx`): на мобиле прижат к верху →
  `top-[calc(env(safe-area-inset-top)+1rem)]` (десктоп — по центру). БЫЛ `top-4` → лез под бар.
- **Dialog** (`ui/dialog.tsx`): центрирован, но высокий мог переполнить под бары →
  `max-h-[calc(100dvh-env(safe-area-inset-top)-env(safe-area-inset-bottom)-2rem)] overflow-y-auto`.
- **SaveBar** (`sticky bottom-0`): `pb-[calc(0.75rem+env(safe-area-inset-bottom))]` (home-indicator).
- **Ридер** (`ReaderPage`, `fixed inset-0`): тулбар `pt-[calc(0.5rem+env(safe-area-inset-top))]`
  (контент iframe ниже — immersive).
- **Toaster** (sonner `top-right`, `main.tsx`): CSS-override в index.css
  `[data-sonner-toaster][data-y-position=top]{top:calc(env(safe-area-inset-top)+1rem)}`.
- **Radix-поперы** (`ui/dropdown-menu`/`popover`/`tooltip`): `collisionPadding={safeCollisionPadding()}`
  (`lib/safeArea.ts` — меряет инсеты проб-элементом, т.к. env() из JS недоступен; 0 на десктопе).
⚠️ Все оверлеи на shadcn-примитивах (Sheet/Dialog/Popover/Dropdown/Tooltip/CommandPalette+Toaster) —
покрыты централизованно: новый оверлей на этих примитивах safe-area получает автоматически.
⚠️ Playwright/Chromium даёт `env(safe-area-*)=0` (как десктоп) — реальные инсеты только на
iOS-устройстве; визуально проверять симуляцией (инъекция `top/padding:47px`) или на айфоне.

### 19. Локальные оверрайды метаданных — МАТЕРИАЛИЗАЦИЯ в колонку, не query-time

Ручная корректура каталога (только админ, глобально): `metadata_overrides` (миграция
**0028**) + `metadata.OverrideController` (`metadata/overrides.go`). Правка **материализуется
в реальную колонку** (`books.*`/`works.*`) — иначе НЕ попадёт в Meili (индексы строятся из
колонок, query-time-join туда не дотянется); бонусом обогащение (`COALESCE` set-if-null) не
перетирает непустое значение. Леджер хранит `original_value` (захват ДО первой правки;
повторная правка его НЕ перезахватывает) → откат + индикатор «изменено». API под
`requireAdmin`: `POST/DELETE /admin/overrides` + `GET /admin/overrides?work_id=` (индикаторы) +
`POST /admin/overrides/revert-all`. Фронт: `useSetOverride`/`useRevertOverride`/`useOverrides`
(`lib/admin.ts`) + `InlineEditableField` — **визуально незаметно по умолчанию** (правят редко,
карточку читают): десктоп — карандаш на ховере у значения, мобила — лонг-тап → action-меню
(«Редактировать»/«Отменить правку»), правка **in-place** (без отдельной панели). Применён к
заголовку (`layout='heading'`, оборачивает `CardTitle`), году в `CardSignalRow`, полям издания
в `EditionRow`/`FileDetails`. Не-админ видит обычный текст. **План —

### 20. Внешние провайдеры: транзиентная ошибка ≠ «не найдено» (иначе отравление lookups)

Провайдеры обогащения (`metadata/*_provider.go`, `fantlab.go`, `wikidata_*.go`) на HTTP-не-200
ОБЯЗАНЫ различать: **404 → `ErrNotFound`** (честное отсутствие для path-запросов `/isbn/{isbn}.json`,
`/works/{key}/ratings.json`; search-эндпоинты не 404), **429/400/403/5xx → `ErrUpstream`** (транзиент/
битый ключ). Хелпер — `metadata.statusErr(code)` (`types.go`). Почему это критично: backfill-воркеры
(`cover/external_rating/year/renown`) на `ErrNotFound` пишут `book_*_lookups.outcome='not_found'` с TTL
90 дней, на прочие ошибки — `'error'` (короткий ретрай). Раньше провайдеры возвращали `ErrNotFound` на
ЛЮБОЙ не-200 → один 429/битый ключ отравлял книгу как «не обогащается» на 90 дней. **Реальный прод-кейс
(2026-07):** GB-ключ в `.env` был обрезан (`zaSy…` вместо `AIzaSy…`) → `400 API_KEY_INVALID`; плюс
`GoogleBooksProvider.FetchRating` ЗАБЫВАЛ `addKey` → рейтинг-запросы уходили анонимно (429). Итог: 110k
GB `not_found`, 0 вызовов под ключом в консоли Google, воркер их не перепроверял. Фикс: `statusErr` во
всех провайдерах + `addKey` в FetchRating. Marker-воркеры (bio/photo/adaptations, single-shot по
`metadata_fetched_at`/`adaptations_fetched_at`) — тоже НЕ помечают попытку при транзиенте (флаг
`transient` в `EnsureAuthorBio/Photo/Adaptations`). ⚠️ Уже накопленные `not_found`/`error` фикс НЕ
чистит (в пределах TTL) — после деплоя жать «Сбросить неудачные попытки» в админке, чтобы перепройти.
⚠️ Урок: `--force-recreate` на прод-контейнере с NFS-томом (`skriptes_books`, addr по hostname) может
уронить его, если DNS хоста не резолвит адрес тома (латентно до рестарта) — не пересоздавать прод-контейнеры
без нужды.

**Прерыватель по хосту (#299).** Все HTTP-клиенты обогащения — `metadata.SourceHTTPClient` /
`NewEnricherHTTPClient` (транспорт `breakerTransport`, `metadata/source_breaker.go`; общее состояние на процесс,
ключ — `URL.Host`). 5 сбоев подряд (сеть, таймаут, 429, 5xx; 404 — не сбой, отмена `context.Canceled` — не в счёт) →
пауза 5 мин, после паузы один пробный запрос, провал — пауза вдвое (до 6 ч), успех — закрыт. Пока пауза, запрос не
уходит в сеть и возвращает `ErrSourcePaused` (`*SourcePausedError`, через `url.Error` ловится `errors.Is`): воркеры
пропускают книгу молча — без записи `error` в учёт и без строки в логе (`case errors.Is(ferr, ErrSourcePaused)` в каждом
воркере), `RecheckPosterHoles` останавливает проход, метрика исхода — `paused`. Лог — одна WARN на паузу и INFO на
восстановление; метрики `skriptes_external_source_up{host}` / `skriptes_external_source_pauses_total{host}`, алерт
`SkriptesSourcePaused` в Grafana хоумлаба. ⚠️ Новый провайдер — только через `SourceHTTPClient`, не голый `http.Client`.

### 21. Воркеры с lookups-учётом выбирают кандидатов уже с учётом срока — в SQL

Год / обложки / внешний рейтинг / язык оригинала / известность: `fetchBatch` отбирает
только кандидатов, которых ПОРА спросить хотя бы у одного включённого источника —
`dueCond` + `dueArgs` (`metadata/lookup_due.go`, те же правила, что `lookupTTL.isDue` в Go;
контракт SQL≡Go держит `TestDueCond_MatchesIsDue`). Раньше срок проверялся только в Go
(`processOne → isDue → continue`), и проход раз в 30 минут перечитывал ВСЕХ кандидатов
охвата батчами с `array_agg` авторов — DMZ (552 тыс. изданий) держал Postgres на ~100% CPU
при нуле запросов наружу (#244). Новый воркер с lookups-таблицей — только так. Источник,
который сейчас спрашивать нельзя (GB за дневной квотой), в список `dueArgs` не передаётся.
Лог `pass complete` пишется только при реальных запросах: `candidates` (выбрано) и
`lookups` (запросов к источникам).

**Что уже известно — не спрашиваем заново (#294).** Исход `native` (`outcomeNative`) —
окончательный ответ «дозаполнять нечего» (язык оригинала совпал с языком издания), в
`isDue`/`dueCond` не перепроверяется; раньше натив писался `not_found` и переспрашивался по
TTL вечно. Воркеры года и языка оригинала берут из выборки `wdHintColumns`: QID работы из
`works.ext_ids->>'wd_qid'` (его находят Tier-2 группировки и «Известность») уходит в
`BookQuery.WikidataQID` — `resolveBookQID` не ищет книгу по названию; свежее «не найдено»
Tier-2 группировки по той же книге (моложе своего TTL not_found) записывается как
`not_found` без запроса (`wikidataShortcut`, метрика с исходом `reused`) — только для книг без
`src_title`: с ним запросы группировки и воркеров различаются. Экранизации берут QID работы в
`EnsureAdaptations`. `isQID` не пускает в SPARQL чужое значение ext_ids.

**Решения владельца по #294** (данные прода 2026-10-03): обход «сначала ядро, потом хвост»
(`corePhases`, `enrichPhase` в `enrichment_priority.go`) у года, языка оригинала и внешнего
рейтинга; в хвосте «не найдено» — не чаще `tailNotFoundTTL` (год), срок из настроек — для
ядра (`lookupTTL.forPhase`, фазовый срок идёт и в `dueArgs`, и в `processOne`); у Tier-2
группировки тот же пол срока (`WorkGrouper.notFoundTTL`: кандидаты — работы из одного издания).
Внешний рейтинг выбирает только книги, которые GB/OL могут найти (`findableAbroadCond`: ISBN,
`src_title` или язык не ru/uk/be — 89 % находок OL, а русские книги без них дали 87 находок на
202 тыс. запросов). OpenLibrary у «Известности» не спрашивается о работе с таким же
«ненаходимым» изданием-представителем: исход `skipped` (`outcomeSkipped`, окончательный, снимает
«Сбросить неудачные попытки»).

### 22. Тёзки: автор = (имя, уточнение); прежняя запись достаётся наследнику

librusec с выпуска 2026-09 различает тёзок уточнением в скобках в фамилии: `Антоний [Блум]`,
`Гибсон [фантаст]`, `Афанасьев [#17465]` (номер — не толкуем). Парсер (`inpx.splitNameNote`)
кладёт его в `Author.Note`, фамилия и `normalized_name` — БЕЗ скобок (по ним идёт внешнее
обогащение); в базе — `authors.name_note`, уникальность `(normalized_name, lower(COALESCE(name_note,'')))`
(миграция 0040). Почти всегда это не «пометка того же человека», а РАЗДЕЛЕНИЕ склеенных тёзок
(на реальном выпуске 677 из 682 имён). Поэтому ДО импорта такого INPX
`importer.planAuthorSplits` выбирает наследника прежней записи (id, подписки, известность): больше
книг прежней записи в файле → ничья: вариант без уточнения → активность пользователей на книгах →
больше книг в файле → по алфавиту; решения — в `author_splits`; у разделившейся записи сбрасываются
bio/photo/metadata_fetched_at (решение владельца — могли прийти от любого из тёзок). Запись без
уточнения из старого файла ложится на наследника (`existingPlainAuthor`). После импорта:
`fixWorkPrimaryAuthors` и `syncWorkSeries` (импорт сам НЕ обновляет автора/серию работы) +
`deleteEmptySeries`. Показ: `books.DisplayNote` — номера `#NNN` не отдаём наружу нигде (решение
владельца); поле `note` у автора в карточке/списке/подсказках/ссылках книги.
**Дубли авторов — ручное слияние (#308).** Один человек под двумя записями: «Лукьяненко Сергей» и
«Лукьяненко Сергей Васильевич», «Конан Дойл Артур» и «Дойль Артур Конан». Кандидаты
(`catalog/author_duplicates.go`): «ФИ» ↔ «ФИО» с совпадающими фамилией и именем (на проде 3 тыс. пар)

карточке автора (`components/AuthorDuplicates.tsx`, `GET /api/admin/authors/{id}/duplicates`) и вкладка
«Дубли авторов» (`/admin/authors`, `GET /api/admin/authors/duplicates`), диалог `MergeAuthorsDialog`

(признак липкий — берётся и из базы, но стоп-лист сильнее); «циклы»-обрывки
сливаются (подписки переносит `moveSeriesSubscriptions`, работы — `syncWorkSeries` (и новую серию, впервые проставленную выпуском, #275), пустые
удаляет `deleteEmptySeries`). Tier-1.5 группировки работ такие серии игнорирует. Карточка автора:
флаг `multi` у серии → не среди циклов, книги — «Вне серий», сами серии — свёрнутым блоком в самом
низу (`MultiSeriesSection`); страница серии — «Межавторская или издательская серия», в шапке ≤5
авторов + «и ещё N»; книги — порциями по 100 («Показать ещё», любая серия) и выбор сортировки номер/год/название
(`SeriesPage::SeriesBookList`, #311; ответ API — все книги, SQL 67 мс на 2,7 тыс.). План —
`~/projects/plans/skriptes/archive/inpx-2026-09-authors-series-plan.md`, issue #257.

Серии сборников (#448, 2026-10-08): альманахи, антологии, номера журналов — в каждой книге десятки авторов, а первых
авторов меньше трёх («Урал улыбается» — 2 книги по 53–59 авторов), и по правилу первых авторов серия оставалась «циклом»
у каждого. Второй признак в `planMultiSeries`: в половине книг ≥ `anthologyMinBookAuthors` (3) авторов и всего ≥
`anthologyMinSeriesAuthors` (6) разных. Сухой прогон на проде — 365 серий; соавторские циклы (двое на книгу) не задеты.
Применяется импортом INPX, поэтому гейт полного переимпорта `reimport_series_rules_v2` (~1 ч на проде).

- **Серия на карточке книги — только авторский цикл** (#468, правило владельца 2026-10-09). `series.kind`:
  NULL — цикл, `'multi'` — межавторская, `'publisher'` — издательская одного автора.
  - Классификатор `'publisher'` — `metadata/series_kind.go::ClassifyPublisherSeries`: название
    («<Автор>. Сборники», «Собрание сочинений», «Избранное», «Новые переводы») или устройство (≥2 работ, ни
    одной с номером, у большинства есть издание того же языка вне серии). Сомнительное — цикл: спрятать
    настоящий цикл хуже. Разовый гейт `publisher_series_v1` и шаг после импорта; у затронутых работ серия
    пересчитывается (цикл важнее).
  - Показ: индекс works отдаёт `series`/`series_id` только у цикла (поиск по названию любой серии
    остаётся — `series_s`); карточка (`books.Get`) — `JOIN series … AND s.kind IS NULL`; PG-списки (история,
    полки, промпты оценок) — так же. Страница автора: `multi` в списке серий = любая не-NULL серия
    (свёрнутый блок внизу).
  - Не сделано: при нескольких циклах работы выбор цикла на языке карточки («Эркюль Пуаро», а не
    «Hercule Poirot») — порядок по-прежнему `(kind IS NULL) DESC, ser_no, id`.

### 24. Премии — только белый список владельца

Раздел «Премии» и плашки показывают только премии и номинации из `awards.Catalog` (`backend/internal/awards/catalog.go`).
Список составлен по досье `~/projects/plans/skriptes/awards-dossier.md` и принят владельцем 2026-10-07: правило
владельца — «без моей проверки не отображаем». Отсюда:

- новую премию, номинацию или снятие ограничения «по 2021» (премии, сменившие курс после 2022: «Интерпресскон»,
  «РосКон», «Филигрань», «Зиланткон», «Нацбест», «Аэлита») — только после его проверки, с досье;
- «Большая книга», «Книга года», «Слово», «Полдень», «Басткон», «Новая фантастика» — отвергнуты, не возвращать;
- пометок (иноагент и т.п.) не ставим — решение владельца;
- номинации — тоже белым списком по id Фантлаба: книжные, без журналов, фэнзинов, постановок, художников,
  редакторов, издательств, спецпризов и «антипремий» (у «Зиланткона» есть «Антизилант»).

Источники (2026-10-08, #439): Фантлаб (`sync.go`), Wikidata (`wikidata.go`: P166 + год P585; награда то на работе, то
на человеке «за работу» P1686, то на человеке без работы — тогда премия автору; книжная премия позже публикации > 5 лет —
ошибка данных, пропуск) и список в репозитории `awards/manual.json` («Дар», «Просветитель», Премия Андрея Белого — по
русской Википедии; обновлять руками раз в год; от премии отказавшихся не вносим — Мария Галина, «Дар» 2025). Кинопремии
(`Award.Film`) — только экранизации книг каталога: фильм лауреата ищется по QID в `book_adaptations`, остальные фильмы в
разделе и в счётчиках не показываются.

Сопоставление с каталогом — precision > recall (как у авторов, грабля №13): без совпадения основы фамилии связи нет.
Основное название без подзаголовка — только для ручного списка: у Фантлаба «Серия. Книга» («Землянин. На службе
Великого дома» — вторая книга цикла) неотличима от «Название. Подзаголовок», и прогон дал ложные совпадения. Отчество
или инициал с точкой у премии автору обязательны («Василий И. Аксёнов» — не Василий Павлович; «О'Нил» — не инициал).
Меняешь `match.go` — сухой прогон на проде в режиме только чтения (выгрузка лауреатов → `VALUES` + `matchWorksQuery`/
`matchAuthorsQuery`, сравнение со старым прогоном; так принят первый вариант).
